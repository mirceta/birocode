The Auto checkbox — a server-side hook, not a browser timer

☑️
Auto
RepositoryConfig.AutoUnderstanding (per repo, persisted in repositories.json, default off) · POST /api/understanding/auto
→
🏁
RunSessionService.RunCompleted
the ONE choke point every chat run ends through — user send, autopilot, loops, arch sends; carries {repoId, lane, status, sessionId}
→
🪝
AutoUnderstandingTrigger
hosted service; fires only when lane = builder, status = done, sessionId present, flag on; never throws; never fails the turn
→
⏳
EnqueueLatest
idle → start; running → ONE pending slot with the newest session (coalesce, never queue); the finishing run chains it; audited as actor "auto"

Recursion is impossible by construction: the helper run is ephemeral and never completes a RunSession, so it never re-triggers itself. The chat module knows nothing about this module (dependency direction understanding → chat).

What the Goal app shows (the visualisation, built by the same convention)

  • 🎯 The current goal in one sentence, plus the acceptance ("done looks like …") the Operator gave.
  • 🧭 Where we are against it — the subagent's reading of the conversation: what is done, what is left, what drifted (a small interactive map, not a wall of text).
  • 🕰 Revisions — when the goal was set and every change since, each with the turn that caused it.
  • 🔗 Links — the board card(s) this agent is a leg of (PR #115's my_effort already knows them), so the per-agent goal and the fleet card can be read together.

One "companion app" family, two kinds — the recommended shape

The Operator asked for "the SAME shape" and "reuse, don't reinvent". The cheapest faithful mirror is a copy (GoalJobs, GoalAsk, AutoGoalTrigger, GoalApp…). The better one is to make the existing classes take a kind:

CompanionKind { id: "understanding" | "goal",
                 folder: "understanding-app" | "goal-app",
                 flag:   AutoUnderstanding | AutoGoal,
                 op:     "understanding" | "goal",           // Console + audit
                 prompt: (cwd, transcript, previousGoal?) → string,
                 capability: understandingAgent | goalAgent }

CompanionJobs   : one job per (repo, kind), same StartOrJoin / EnqueueLatest / pending slot
CompanionAsk    : same transcript paste/export + AgentHelperRunner; the prompt comes from the kind
AutoCompanionTrigger : one RunCompleted subscriber, fires each kind whose flag is on
HarnessStaticApp: already generic — GoalApp is UnderstandingApp with another folder
🧠
understanding
unchanged behaviour; only its internals move behind the kind
🎯
goal
the same run with a different prompt, folder, flag and Console op — plus the goal store it reads and writes
🔮
later kinds
the same family could carry "risks", "decisions", "plan" apps at zero infrastructure cost

Cost to be honest about: with BOTH Autos on, every completed builder turn starts two paid agentic runs. Tab 5 asks whether the goal run should be cheaper (a read-only pre-check that answers "no change" without building) or gated.

What the subagent is given for a goal run (proposed)

  1. the conversation transcript — exactly as the understanding run gets it (pasted ≤12k chars, else exported);
  2. the current goal: goal-app/goal.json ({text, acceptance, setAt, setBy, revisions[]}) if it exists — pasted into the prompt so the run does not have to find it;
  3. the convention doc (absolute path, resolved through the playground ancestor like today) with the folder name goal-app/;
  4. the rule: decide SET / REVISED / UNCHANGED from the turns since setAt; on SET or REVISED rewrite goal.json + index.html; on UNCHANGED write nothing and reply "GOAL UNCHANGED"; never touch anything outside goal-app/.
