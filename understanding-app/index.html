The startup handle race — why loops "silently never started"

openspec change fix-startup-handle-race · diagnosed 2026-07-28 on live with stack + heap dumps

What the operator saw

A goal loop armed from the phone, every gate green — and zero iterations, forever. No [LOOP] log lines, no errors, engine.state null. Meanwhile the web UI worked perfectly, which is exactly what made it confusing: the API answered, so the harness looked healthy.

Actually broken

  • Desktop GUI: frozen (deadlocked in SetParent)
  • Autopilot engine: parked on its first 3-second delay — for 76 minutes
  • Collector poller: frozen the same way

Still healthy (the mask)

  • Kestrel API on :5099 — the phone UI worked
  • Chat runs, file browsing, everything request-driven

Why it comes and goes

It is a startup race: most restarts win it and everything works. A deploy restart with a phone actively polling the instant Kestrel comes up can lose it. That is why earlier loop tests passed and the 10:19 deploy produced a broken process — same code, different coin flip.

What was proven, and how

  • Diagnosis — dotnet-stack + dotnet-dump dumpasync on the live process: main thread in SetParent, engine state machine at <>1__state = 0 (first delay) 76 minutes after start, continuation posted to a queue nobody pumps.
  • Fix verified on an isolated harness (:5218) — at t+3s the engine's first tick ran and logged mining transcripts in background...; mining finished 64 s later (378 routine prompts from 257 sessions) while ticks continued; collector poller started; API health 200; GUI responsive.

The startup log, healthy shape

[10:59:26] [SERVER] Kestrel running on http://0.0.0.0:5218
[10:59:26] [COLLECTOR] poller started
[10:59:29] [AUTOPILOT] mining transcripts in background...   ← first tick, 3 s in
[11:00:33] [AUTOPILOT] mining done in 64s (378 routine prompts from 257 sessions)

If a future process ever shows the server lines but never the [AUTOPILOT]/[COLLECTOR] lines, the engines are not running — that is the old signature.
