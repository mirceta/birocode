Why autopilot loop prompts don't render in the chat

Investigated 2026-07-28 against the live goal-loop test (repo "Claude Web", session 194f3269, sends 08:53–08:54 UTC). Two separate causes.

Two send paths — only one draws the user bubble

The backend SSE contract (CliRunnerService) has no user-message event: it emits session / thinking / tool / token / usage / done. The user bubble you normally see is drawn client-side by the composer (sendTo() in ChatContext.jsx) before the stream starts. An autopilot loop send never goes through the composer — the open page discovers the run via the 5s reconcile() poll and calls attachToRun(), which only appends an empty assistant bubble and streams the reply into it.

So the two symptoms decompose as:

"Prompts only appeared after a full refresh" — refresh reloads the transcript from disk (loadTranscript), and sends 2–4's user lines are on disk. Live, nothing ever draws them (cause 1).

"Even after refresh, the first one never appeared" — send 1's user line was never written to the .jsonl by claude.exe (v2.1.220). The reply "OK" and the last-prompt record are there; the user entry is not. The harness renders the transcript faithfully — the data is genuinely absent on disk. This is a CLI persistence quirk on the first resumed -p run, not a harness render bug.

The fix — one synthetic event, one client case (implemented & verified)

Shipped as openspec change fix-loop-prompt-render; e2e-verified on isolated :5227 (verify-loop-prompt-render.mjs, 12/12 PASS): a sleeper-stub claude.exe that never writes transcripts proves the bubble comes from the new event, not the disk.

Backend (fixes live rendering + reattach replay)

In AutopilotService.SendPrompt, right after the run slot is claimed and before _cli.RunAsync, emit the prompt into the run's seq-numbered buffer:

await session.EmitAsync(new { type = "user", text = prompt, actor = "loop" });

Because it lands in the RunSession buffer it is (a) broadcast to any attached client, and (b) replayed to a client that attaches later via ?after=N — so the 5s poll's attachToRun gets it for free.

Frontend

In makeEventHandler (ChatContext.jsx) add a case 'user': insert a user bubble before the trailing streaming assistant bubble (attachToRun appends the empty assistant bubble before replay starts, so the insert must go one position up).

What this does NOT fix

The first-send user line missing on disk (CLI quirk). After a full page refresh the transcript is still the source of truth, so a prompt the CLI never persisted stays absent there. The harness's own durable record of every loop send exists in autopilot-audit.jsonl if we ever want to overlay it into transcript reconstruction — but that is a separate, larger change.
