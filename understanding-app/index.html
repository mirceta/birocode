The chat.focus event

openspec change add-chat-focus-event — the feed's third event type, and its first browser-originated one: the moment the End User clicks into an agent dock's chat textbox, so the sound system can cue it.

The path an event takes

browserDock composerChatInput.jsx textarea gets an onFocus — dock-embedded only; the main chat page never emits.
browserDebounce gateOne emit per composer per 10 s (module-level timestamp). Fire-and-forget — errors never disturb typing.
HTTPPOST /api/events/chat-focusThe feed's single, fixed-type write endpoint. Session-authed; type is set server-side, repo from X-Repo-Id.
backendHarnessEventFeedPublish("chat.focus", …) — same envelope as the turn events, best-effort, soft-capped.
backendCollectorSelf source ingests it into the aggregate; HostEventSound.Notify fires the host cue.
browserevents-appNext poll renders it and playCue("chat.focus") plays the device cue.

Hear the cues (device layer, same synth as events-app)

Host layer counterpart: beep mode plays the Windows Question sound, voice mode says “someone is writing to agent <source>”, and the Event → sound rules table has a chat.focus slot for a custom file — precedence: custom file › voice/beep.

Why a write endpoint, when the feed is “read-only”?

Every publisher so far was backend code (CliRunnerService around agent turns). But focusing a textbox exists only in the browser — the server can't observe it. So the spec's “feed reads are authenticated and expose no new actions” requirement was amended with one narrow carve-out:

GuaranteeHow it's kept
No arbitrary publishingThe endpoint accepts no type — it can only ever append chat.focus. Clients can't forge turn.ended.
No harness actionsAppending one best-effort event is the entire effect. Nothing else happens.
AuthenticatedSame session gate as every /api/* route — verified: unauthenticated POST → 401, nothing appended.
No feed floodingClient-side 10 s cooldown per composer + the feed's existing soft cap.
