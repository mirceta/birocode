One watchable eval suite, three scenarios built

We folded our golden-example eval into main's shipped loop-eval suite. It's now the third scenario — golden — beside goal and queue: runnable as an automatic test, live, and watchable from the Tests tab.

Understanding app for feat/loop-evals after the rework (OpenSpec design D6). Supersedes the earlier "two competing approaches" version.

Ground truth: synthetic fixture + check script.

Score: binary.

Replay a captured human-babysat task from its git bundle; the loop must reach a state where every acceptance check passes.

All three share one contract — so all three run the same three ways

automatic isolated test — live against the running harness — startable + watchable in the Tests-tab runner

Because a scenario just emits @@LOOPEVAL@@ verdict lines, answers --describe, and binds a dock tab, the C# runner lists it, streams its state (preflight → armed → running → passed/failed), and a human watches the driven conversation live. golden conforms to that contract, so it inherited all of it. The only registration needed: one line in LoopEvalRunnerService.Scenarios[] (the client list is dynamic).

What golden adds that goal/queue can't

goal and queue ask "can the loop finish a canned synthetic job?" golden asks "how close to a real human did the loop drive on real captured work — and how reliably?"

  • Real ground truth — the fixture is a git bundle captured from an actual babysat session (start state · plan · per-turn commits · labeled transcript), authored in the curation UI.
  • Trajectory evidence — the loop's own per-step commits are compared to the golden commit chain (files-touched overlap, first divergence). Reported, never a pass/fail — a correct run may validly diverge.
  • Reliability — --runs N (isolated) reports pass-rate + iteration spread across repeats.

The rework: keep the ground truth, replace the runner

Our original work had a great authoring layer but a weak execution layer (an offline in-process console). The rework keeps the former and rebuilds the latter on loop-eval.

KEEP
Golden-example bundle format (manifest · plan · conversation · repo.bundle) and the curation UI + endpoints (api/loop-evals) that capture a real session. This is the unique asset loop-eval had nothing like.
REPLACE
The standalone in-process console runner (tests/loop-evals/LoopEvals/) — deleted. It booted its own host, ran only from a terminal, and no one could watch it.
NEW
tests/loop-eval/golden.mjs + a few shared helpers in lib.mjs (clone-and-strip, acceptance-check runner, trajectory diff, bundle provisioning), and one catalog line so the Tests-tab runner lists it.

Two mechanics changed as a result

  • Materialization — from copying a synthetic repo-template to cloning a real bundle at eval/start with the answer stripped.
  • Trajectory source — the old runner committed after each turn via an in-process hook; over HTTP there's no hook, so the loop's own per-step commits are the trajectory, diffed against the golden chain fetched from the bundle.

Reliability stayed, but as an isolated-only --runs N sweep; live mode is one watchable run.
