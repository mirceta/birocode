Fleet arch agent: standing on the event feed

The single-machine arch agent shipped (add-arch-agent, feature/arch-agent). The next question: how much of the harness event feed + collector does the fleet version reuse, and should the agent live in the events app instead of the harness? Short answer: the read half is already fleet-shaped, the write half doesn't exist, and the agent should stay in the harness.

Two stacks that already touch

Everything below is shipped and running. The arch agent already drinks from the collector — it was a deliberate design decision (D2 in add-arch-agent/design.md: "the fleet arch reads the same shape over HTTP"). Toggle the highlights to see each stack.

The feed contract is genuinely open

Envelope {seq, at, type, source, data}; the collector never parses data — it pages any producer honoring the shape (docs/event-feed-contract.md exists precisely so third parties can join). Types in circulation: turn.start, turn.ended, chat.focus, arch.wake.

The "dock" you remembered

The subscribed-harness list + merged feed + agent cards is events-app/index.html — a build-less SPA polling /api/collector/events. It holds no state and no logic worth reusing server-side; the real machinery (subscriptions, watermarks, credentials) lives in CollectorService, which is exactly what the fleet arch needs.

Net: the fleet arch's entire sensory system is already built and battle-tested

Subscriptions, transport, identity, fleet board — reuse without modification. What does not exist anywhere: an outbound command channel (send a task to a repo agent over HTTP), actor provenance across the wire (a remote send would render as a human bubble in the remote dock), and remote availability (git state of a repo on another machine).

Should the arch agent live in the events app?

Three candidate homes. The question dissolves a bit once you see that the "event feed app" is two very different things: a stateless browser page (events-app) and a backend service (the collector) — and the arch agent already sits next to the collector.

A · Inside the events app SPA

rejected

  • It's a static page with no backend of its own — it cannot run a standing CLI session, hold credentials, keep a watermark, or write memory.
  • Alive only while a browser tab is open. That's exactly the fragility the detached-runs work eliminated (backend-owned RunSessions so closing the phone kills nothing).
  • Everything the agent needs — run slot, autopilot engine, loop-eval gate, audit log, MCP server — is backend.

B · Standalone fleet-arch product

rejected for now

  • Architecturally pure: a separate process speaking only event-feed-contract.md + harness HTTP, deployable anywhere, no favored machine.
  • But it re-implements what the harness gives free: CLI runner, session persistence, autopilot ladder, eval harness, auth, deploy (swap.ps1), UI.
  • And it orphans the just-shipped in-harness arch agent. Wrong cost/benefit while the fleet is ~2 machines. Revisit if the fleet outgrows "one operator, one LAN".

C · Stay in the harness; any harness can be the fleet arch

recommended

  • The arch agent already rides harness mechanics (synthetic @arch repo, run slot, loops) and already reads the fleet-shaped collector aggregate.
  • Fleet = scope widening: drop the self-only filter, add an outbound send client. Matches the design's own promise ("change of scope, not redesign").
  • The operator designates which harness runs the fleet arch — same pattern as the collector itself (every harness can collect; yours does).

The realization that settles it

"Host the arch agent in the event feed app" is really asking "should the arch agent live next to the collector?" — and it already does. Both are services in the same harness process; the arch agent's wake source is the collector. The part of the events app worth anything to an agent (subscriptions, merged feed) was never in the SPA — the SPA is a projector. So option C isn't a compromise; it's recognizing that the co-location you're asking for shipped last week.

One genuinely good idea to salvage from option B: keep the fleet arch's dependencies expressible in wire terms (events in, HTTP sends out), so extraction to a standalone product later stays cheap. The new outbound send client should be written against peer HTTP APIs even for machine="self"-adjacent thinking — but per D1, local sends keep the in-process run-slot path; only remote sends go over the wire.

The fleet shape this implies

Availability across machines

The rule stays available | busy | claimed | unmanaged. Busy-ness of remote repos falls out of the collector (turn.start/ended pairing — the status board already computes it). Claimed needs remote branch state: either a git.state event published on branch change, or the send client asking the peer's git API on demand. The design already picked remoteUrl as the cross-machine repo identity (D5), so "find a free machine for this repository" = filter agent views by remoteUrl, then by availability.

What deliberately does not change

  • Local sends keep the in-process run-slot path (D1) — no loopback HTTP for machine "self".
  • The collector stays read-only; no push transport appears anywhere.
  • The fence (--disallowedTools + MCP-only tools) is unchanged — send_task just grows a working machine argument.
  • One fleet arch per fleet by convention, not by mechanism — same as "every harness can collect, yours does".

The gaps — and what was built (change add-fleet-arch-agent)

The four steps below shipped together as one OpenSpec change; the fifth stays deferred. Tags say what landed.

  1. Remote wake input built The SelfId filter is gone from ComposeWakeCore: an event's key is the bare repo id on the self source and sourceId/repoId on a subscribed harness; managed scope = local ids ∪ fleet keys (arch.json: managedFleet). Wake lines say "on <machine>".
  2. Remote agent views built — via the peer describe, not a new event Every harness now answers GET /api/arch/peer with protocol, build version, machine, accept-sends, gate state and all its repos with availability it computed itself. A FleetClient caches that per source (5 s); tool calls refresh it, the engine tick never blocks on a dark peer (it shows unreachable).
  3. Outbound send channel built — FleetClient beside the collector Borrows the collector's address + stored credential through BuildPeerRequest; the collector itself still only GETs. Gated by the per-source allow sends flag (events app button + Arch tab Fleet card). send_task machine:<label> resolves by source label or id, applies A's checks (armed, managed, allow-sends, deny list) and POSTs to /api/arch/peer/send.
  4. Actor provenance on the receiving side built — peer API, not an actor field on the chat POST The receiver computes the actor arch@<from> itself and writes its own audit row (kind arch, phase fleet:<from>), so a caller can never post a bubble that claims to be human and the tag survives reloads. Receiving is an opt-in: accept fleet sends + the host-only autopilot gate; B's deny list, claimed rule and run slot all apply.
  5. Arch-to-arch (L2 proper) still deferred Not needed for "told a repository and a task, find a free machine": the fleet arch talks to remote repo agents directly. Revisit when one machine's arch should delegate to another's.

Ship gate: tests/loop-eval/fleet.mjs

Two isolated harness instances on one box (A :5210 hosts the fleet arch, B :5211 hosts a goal-fixture repo agent). B refuses a peer send before opting in; A subscribes to B with B's password and allows sends; A's arch is scoped to B's repo, armed in drive mode, told to get the goal check green. Asserts: the goal check passes on B; B's audit carries the send with the fleet phase and B's dock shows arch@<A>; A's collector carried B's turn.ended; an arch.wake followed; A's audit holds the fleet send. The live two-machine run is the Operator's after deploying this build to the second box.

Two things to name in the proposal's risk section

  • Credential blast radius: a source credential is the peer's full API password. Watching already implied holding it; sending makes it hot. The per-source opt-in flag is the mitigation; a scoped send token would be the real fix, someday.
  • Feed durability: events live in RAM (ring 1000, lost on restart). Fine for wakes (the watermark just resumes), but the fleet arch must never treat the feed as history — read_transcript and git_state stay the source of truth, same as today.
