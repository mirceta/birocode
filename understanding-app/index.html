How a badge click opens a tab today

🃏
the chip on the card
KanbanBoard.jsx · focusAgentTab(key, href) where href = <that machine's harness>/studio?agent=<repo> (never guessed: the peer registry's address)
→
🪟
window.open('', 'birocode-agent-<key>')
a NAMED target, no features — Chrome opens a new tab in the opener's window (the dashboard's), or finds the existing one
→
🧭
navigate only a fresh one
an existing tab is found and focused wherever it lives (any Chrome window, any monitor — engine-verified), never reloaded
→
😩
the pain
a BRAND-NEW agent tab always appears in the dashboard's window (right monitor); the Operator drags it to the left window every single time

Nothing here is a bug: a page can only open into the window that hosts it. The fix is a setting, not a patch.

Feasibility, honestly

abilityweb pageextensionwhat we do

place that window on a chosen monitor⚠️ Window Management API: getScreenDetails() + left/top — needs a secure context (https / localhost) and a one-time permission✅screen picker when available; otherwise the window opens on this screen and the Operator drags it once — it keeps its place while it lives
focus a tab that lives in another OS window✅ (proven in check-agent-tabs.mjs)✅"tabs" mode keeps doing exactly this
possibleconditionalimpossible from a page

The dashboard is usually reached over http on a LAN address — not a secure context — so the screen picker is expected to be unavailable there; the Settings tab detects this live and says what to do. Over https or from localhost the picker works.

    Open questions
    
  
    
    
    Q1 · Tabs inside the dedicated window?
    "window" mode is one viewer window: each click shows the clicked agent there (one page at a time). Per-agent tabs inside a window on the other monitor is the extension route. Is one viewer enough, or do you want the extension?
    
    
    Q2 · https for the dashboard?
    The screen picker needs a secure page. Do you reach the dashboard through the IIS proxy over https anywhere? If not, "drag once, it stays" is the reality on http.
    
    
    Q3 · Popup-style window
    A positioned window has no tab strip (Chrome's popup type). Acceptable for a harness viewer? The Operator can still Ctrl+L / use the harness's own navigation.
    
    
    Q4 · Per-browser setting
    The choice lives in this browser's storage like the dashboard layout. Should it also sync to the harness (server-side) so another device inherits it?

    So the two wishes exclude each other with web APIs: tabs need a normal window (not placeable by script), placement needs a popup (cannot hold tabs). The Settings tab offers both viewers; tabs is the default.
