Birokrat tool on any machine — and the Preflight button

What just changed: machine-independent server resolution + a one-click readiness check in the Tools lane
The mechanism was already portable; the configuration wasn't checkable. Two things are new: (1) the harness now finds the Birokrat MCP server purely by the sibling-checkout rule — no absolute paths baked in — and (2) the Tools lane grew a Preflight button that verifies, on the host, all five conditions a chat run needs, and tells you exactly which one to fix.

The sibling-checkout rule

On every machine, the repo that hosts the MCP server is assumed to sit next to your registered repo. The harness probes each registered repo's parent folder — both checkout layouts — and never falls back to a machine-specific path (the old ~/Desktop/playground fallback is gone):
any-parent-folder/ ├── your-repo/ ← registered in the harness └── birokrat-ai-platform/ ← sibling, cloned next to it ├── birokrat-ai-platform/ (nested layout — as on this box) │ └── mcp-server/app/dist/index.js ← resolved ✓ └── mcp-server/app/dist/index.js (flat clone — also probed ✓)
An explicit path in the panel's "MCP server script" field still overrides the probe, for non-sibling checkouts.

New-machine checklist

  1. Install Node.js (on PATH).
  2. Clone birokrat-ai-platform next to your repo; build its mcp-server so app/dist/index.js exists.
  3. Register the repo in the harness; open the dock's Tools lane.
  4. Enter the API key + a URL that machine can reach (LAN http://…:19000/api/v2 only works on that LAN; public default is https://next.birokrat.si/api/v2/). Enable, Save.
  5. Hit Preflight → all green → done. A red row names its own fix.
Your key never travels with the repo — it lives in host app-data (%APPDATA%\ClaudeWeb\tools.json) by design, so step 4 repeats per machine.

Why "Save" hung forever in the Tools lane

Incident of 2026-08-25 ~13:12 · Tools lane save + reload both stuck on the phone
Verdict: your save actually succeeded. The server received the PUT at 13:12:12, wrote tools.json (enabled, key stored, your LAN URL), and at 13:14:03 it already injected the Birokrat MCP config into a live chat run. What broke is the browser: your device had all 6 HTTP/1.1 connections to the harness occupied, so the save's response — and every later Tools request — sat in the browser's own queue forever. The server was idle and fast the whole time.

The one number that explains it

Browsers open at most 6 parallel connections per origin over plain HTTP/1.1 (no TLS ⇒ no HTTP/2 multiplexing). The dock UI is connection-hungry:
WhatHeld forHow many
Chat stream of a running agent (GET /api/chat/stream) entire turn — minutes1 per running dock
Message / status pollers (ChatContext, docks, sounds, flags, clock, traffic…) ~0.1–1 s each, every 4–5 s20+ intervals; several in flight at once
Your Tools PUT / GET queued — never got a slotthe victim
With one or two agents mid-turn (long-lived streams) plus overlapping pollers on a slow phone link, the 6 slots saturate. New fetches don't fail — they wait silently. That's exactly "saving takes years" and "Loading tool settings… forever".

The fix — implemented (openspec reduce-connection-appetite)

  1. Streams multiplexed ✓ — all conversations now ride ONE shared GET /api/chat/stream-multi connection (events enveloped per run), with automatic fallback to the old per-run streams if the endpoint is missing (rollback safety). N running agents now squat 1 slot, not N.
  2. Pollers visibility-gated ✓ — every steady-state poller skips its tick while the tab is hidden; a locked phone generates near-zero traffic. (Consolidating them into one status endpoint remains a future change.)
  3. (Still open, infra) TLS on :5099 would unlock HTTP/2 multiplexing and make the cap irrelevant — a bigger operational change for a LAN harness.
Worst case before: ~4 squatting streams + 21-request bursts vs 6 slots. Now: 1 shared stream + your own send + short-lived polls — saves always find a free slot.
