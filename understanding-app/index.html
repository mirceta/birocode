Hub performance: the log path was the leak, the spin and the crash

Fleet task 3bcaff3a · branch perf/hub-cpu-and-dashboard · openspec hub-perf-log-path. Why the hub sat at 130–140 % CPU, why the dashboards felt slow, what degraded over time — and what the numbers say before and after.

What one dashboard poll did to the host

Two LAN browsers poll the Management App and the Dashboard every 3–5 s across a dozen endpoints. Each request was cheap (the API answers in 1–50 ms). What was not cheap was the log line every admitted LAN request wrote, because that line took three trips:

The activity box is a WinForms RichTextBox: every append re-lays-out a bigger document, so the same line costs more each hour. Past a certain size its native control faults inside ScrollToCaret — an AccessViolationException that no try can catch — and the hub is gone.

The three symptoms, one cause

ReportedWhat it actually was
Proxy at 130–140 % CPUOne core of request work is a fraction; the rest was the UI thread painting the day's log into an ever-larger box, and the logger flushing a syscall per line under a lock every request passes through.
Dashboard slow to loadThe pages were never slow on a fresh process (~100–200 ms warm, same before and after). The host was slow: requests queued behind the logger lock and a UI thread busy with the log.
Degrades over timeThe box grew all day (700 B of RSS per request, for the life of the process), each append got dearer, and on 2026-09-17 and 2026-09-22 the control faulted and the process died.

The hub's own log files

Per-day harness log under run-bin/logs/. The admission line ([IPFILTER] Admitted … via LAN bypass) is one per LAN request; [GIT] is one per git status spawn.

Peak: 25k admission lines an hour from two addresses (192.168.0.101 and .215). A dashboard tab left open overnight kept polling at ~0.8 req/s because eight client pollers ignored document.hidden.

What was not the problem

  • The API. The dashboards' full polling mix (13 endpoints, ~2.6 req/s) costs 9 % of one core on the unmodified build in the lab; no endpoint takes more than ~50 ms even with the collector feed at its 1000-event cap.
  • git. ~4 git status processes a second on the hub (105k lines on the 24th) are real load on the box, but they land in git.exe, not in this process. Deferred — see tab 5.

perf-logpump: N requests that each write one log line

Each build is booted alone with a minimal store; the script pumps requests at concurrency 16 and, every 20k lines, samples process CPU per 1,000 requests, RSS, and the latency of an unrelated call (/api/arch/fleet/status). Two drivers: the LAN admission line (per request before, rate-limited after) and GET /api/files/read, whose [FILE] Read line is still logged per request on both builds — the fair comparison of the log path itself.

Found, not changed here

  • git status spawns — ~4 processes/s on the hub. A per-repo status cache with a short TTL shared by every reader; touches dock, arch and status callers, so its own change.
  • Policeman journal — ~2.5 MB rewritten per pass.
  • TrafficStats — a lock per request around a dictionary update; visible under the pump, not at the hub's rate.
  • Unbounded per-session state — transcript accumulators, SessionService._summaries, PolicemanSweep._said; the message cache holds 24 files against a 64-dock roster. Slopes over days, not hours.

What to expect on the hub after deploying this branch

  • The activity box in the host window shows the last ~400 KB of log and refreshes four times a second instead of per line.
  • The log file gains one Admitted line per LAN address per five minutes, with the request count, instead of one per request.
  • Resident memory stops climbing with the request count; CPU under the same two browsers drops to a fraction of a core.
  • No more AccessViolationException exits from the activity box.
