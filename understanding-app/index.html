The loop parameter panel is the state machine

My understanding of what you asked for — confirmed, and now built on branch feat/loop-state-params (OpenSpec change loop-state-param-panel). The mockup below is what the dock's loop panel now actually shows: open an agent dock's loop popover and pick 🎯 or 📦.

What I got wrong last time: I only built the viewer — a chip strip and a reference diagram — and left the dock's loop parameter subsection as-is: a "Show prompts" toggle hiding a flat dump of text boxes. The actual ask: that parameter subsection itself should be restructured as the state machine — sections named after the states, each holding that state's parameters, the badge we expect the agent to emit there, and an explicit statement of what the loop system does when that badge appears. The little live state readout on the dock header was useful and can stay, but it's the side dish.

What you want

Same pane, restructured. Every parameter lives inside the state that uses it. Each state section reads as: parameters → badge we expect → what emitting it does. The transition dynamics become knowable from the settings themselves. Full mockup below ↓

Also: prompts stop being a hidden "inspection" afterthought — they're ordinary parameters of the loop, shown with the rest.

Decisions baked into the build (say the word to change any)

  1. Code-accurate grouping. Your example put the verification machinery in WORKING_STATE; the engine sends the verification prompt on entering VERIFICATION_STATE and STEP_VERIFIED is the reply that exits it — so that's where they live. The queue's WORKING_STATE shows an explicit badge-less exit trigger ("the step's turn finishes") instead of pretending there's a badge.
  2. Shown as parameters, read-only for now. Badges and templates are compile-time constants in the backend engine — making them editable is a real backend feature. This release renders them as first-class parameter controls; editability is a clean follow-up change.
  3. LOOP-WIDE on top holds goal text, turn cap, queue binding, the verification toggle, and deny-list chips.
  4. verify-owed owns no parameters → no section; it's the transition arrow, but it stays a distinct chip in the armed header strip and lights VERIFICATION_STATE while active.
  5. Scope: dock popover only. The console Loops tab is untouched.
  6. Both live readouts kept: the compact strip in the armed header and the current state's section lighting up with a "● now" pill (verification off dims VERIFICATION_STATE — the machine honestly shows that state is skipped).
