Adding fleet agents is doable, but two facts decide how it would feel, so read tab 1 before saying go.

The phone can only talk to this harness — so this harness relays

The phone is paired with this harness (its session cookie is for this origin only), and the sofa remote's whole contract is "post to this harness". A peer's agents can appear on it only if this harness speaks to the peers on the phone's behalf — which it already does for the arch: the fleet client calls every peer's API with the credential the collector stores (the same one it uses to read their feeds). A thin, allow-listed relay is the natural shape.

List — the remote reads GET /api/arch/fleet/status (the view the Status tab and my_peers use): machines, their agents, availability, reachability. Grouped by machine; a dark machine's agents greyed, never dropped.
2
Write to a peer agent — a relay POST /api/remote/relay/<sourceId>/chat: this harness forwards the prompt to the peer's own POST /api/chat with the stored fleet credential and the right X-Repo-Id. Same for peek (sessions/…/messages), the question buttons, Stop. Narrow allow-list, nothing else proxied.
3
The projector — open-agent {sourceId, repoId}: the big screen navigates to the peer's harness (http://192.168.0.42:5099/studio?agent=…&screen=projector, exactly the link the Kanban chip opens — the home-bridge proxy makes that address reachable from this PC) and from then on listens to the peer's command queue — so this harness relays /api/remote/commands and /screens to the peer too, and the phone's "projector is showing" follows.
!
The catch: login on the peer. The projector browser needs a session on each peer harness it shows (their cookies are per origin). Chrome on the projector remembers a login for 30 days; the living-room WebView2 profile would see the peer's login page the first time. One-time per peer; the relay cannot do it for the browser.

Three sizes of this feature

S · List + message

smallest useful

Fleet agents listed under their machine; tap → the composer writes to it through the relay; peek, questions, Stop through the relay. The projector keeps showing this harness. ~ a day. Nothing on the projector changes.

M · S + the projector follows

recommended

As S, plus open-agent for a peer hops the big screen to the peer's harness and this harness relays commands and heartbeats to it, so 🛋 / ▲ ▼ / zoom keep working there. ~ two days; the login-on-the-peer catch applies.

L · peer UI under this origin

later, if ever

This harness proxies the whole peer UI under its own origin so one login covers the fleet and no hop leaves the page. Heavy (SSE, iframes, the per-process MCP tokens) and it crosses the home/business line the proxy change was built to keep. Not now.

Prerequisites (settings, not code) — or the picker stays empty

Alternatively point the remote at the hub's fleet view by making the hub the harness the phone pairs with.
2

3
Then I build, in this repo only: the relay (allow-listed, with the fleet credential), the remote's grouped list, open-agent with a sourceId, the relayed commands/heartbeats, tests, an end-to-end with two isolated harnesses on this machine (one plays the peer). The living-room app needs nothing.
