An orchestrating agent that lives in its own home repo, is woken by turn.ended events from the repos it manages, and can only act through five MCP tools. It has an Arch tab with Chat and Tools lanes and a live-turn stream.

add-fleet-arch-agent implemented

The same arch agent, now able to manage repos on other harnesses. Each harness exposes a peer API. The caller's collector already knows the peer's address and password, so a fleet client borrows that. Two opt-ins gate every send.

  • Tasks: 14 of 14 checked.
  • Verified on two isolated instances on this box. Not yet on two real machines.

The constraints that make it safe to run

  • Tools are the only medium. The arch session runs with Edit, Write and Bash disallowed and Read fenced to the home repo. It can only observe and send.
  • The receiver owns its rules. A fleet send still runs through the receiver's deny list, its claimed rule, its run slot and its autopilot gate. The caller cannot bypass any of it.
  • Provenance is stamped by the receiver. The bubble tag arch@<machine> and the audit row are written on the receiving side, so no caller can post as a human.
  • The collector stays read-only. Only the fleet client ever POSTs to a peer, and only for a source marked "allow sends".
  • No replay. A fresh arch watermark starts at the collector's current sequence, so arming it does not wake it on history.
