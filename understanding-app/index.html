The living room has the projector and the sofa; the hub (this computer) has the arch and sees every agent in the fleet. Three facts that decide the design

  • Pairing = admin. The sofa PIN mints the same 30-day session a password login gets. Whatever the bridge, the phone must become a viewer, not an admin.
  • A peer's describe is not the fleet. Subscribing the living room to the hub would show the hub's own repos, not the eight peers. The fleet view lives only in the hub's /api/arch/fleet/status.
  • Two segments, one house. The hub's LAN bypass is 192.168.0.0/24; the sofa is on 192.168.1.x. Letting the sofa in means admitting devices, not the segment.

Controls, in one list

  • Separate viewer session kind; every write route and every route outside a short read-only allowlist refuses it (unit-tested list).
  • Opt-in gate on the hub — "accept sofa viewers", default off, next to accept-sends / upgrades / provisioning; one switch turns the whole bridge off.
  • LAN-only for viewer sessions (resolved client IP), devices admitted one by one, never the 192.168.1.0/24 range; 24 h sessions, a revoke list.
  • No secrets in the view: the viewer's fleet status drops account identities, plan usage, peer addresses and credentials; transcripts pass the existing scrubbers.
  • Audit every viewer call (device, route, agent); rate limit the transcript relay; the relay only for agents the hub manages.
  • M2 only behind a second gate and per-agent allowlist; sends go through the hub's own send path under the peer's accept-sends; never deploy / upgrade / provision / settings / approvals from the sofa.
  • Hygiene first: per-peer scoped tokens on the fleet channel instead of each peer's admin password in clear HTTP.
