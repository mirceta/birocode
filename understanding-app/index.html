One occurrence, from the clock to the history row

The scheduler is a hosted service on the loop engine's 10 s cadence. Per card and per tick it takes one decision — idle, hold, fire or skip. Click a step.

Three rules that make it predictable

Fixed grid

Occurrences are anchor + k·every. A run that starts late or takes 40 minutes never shifts the next one. Creating a card does not fire it — Run now exists for that.

One pending occurrence

Harness off overnight, gate closed, agent busy for three hours: the card runs once, for the newest occurrence, and the run says "covers 4 earlier occurrences". Never a burst of replays.

Busy is never a queue

The run slot stays the only arbiter (the arch-agent spec's rule). A due card waits in the scheduler; nothing is stashed in the agent, no running turn is ever stopped.

What already exists — and what it is used for

Why not just…

…a fifth loop kind (cron)?

Loops are turn-end triggered and mean "resend until a sentinel". There is one loop slot per agent, structurally — a schedule needs many per agent. No loop record has an interval field, and the arch loop tools refuse a cron kind on purpose. The only wall-clock send today is the arch "quiet floor", fenced to @arch.

…a Kanban card with a repeat field?

Board cards get delivered: todo → … → pr-merged, verified against git and GitHub, read by the policeman, judged stuck or dishonest. A recurring task never delivers, so every one of those rules would need an exemption. Same look, separate entity — with an optional bridge: a run that ends ATTENTION can create a board card.
