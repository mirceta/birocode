Arch agent as middle management

Operator → Arch agent → Repo agents on one machine now; a fleet arch above that next. The run slot and the git branch decide who may be talked to; the event feed decides when the arch agent wakes; the arch agent has its own home repo and its own tab. Planned as OpenSpec change add-arch-agent.

Three levels, built bottom-up

Repo agents exist. The single-machine arch agent is this change. The fleet arch agent is the next task; it is drawn so this change does not paint it into a corner.

L0 · Repo agent (exists)

Identity
Dock tab: repoId + one Claude sessionId + git remote URL
Slot
One builder turn per repo at a time; a second send is 409
Record
The dock chat is the complete transcript, whoever sent what
Power
Full over its repo

L1 · Arch agent (this change)

Identity
Reserved id @arch, one session, cwd = its home repo
Medium
list_agents, git_state, read_transcript, send_task, remember
Wakes on
turn.start / turn.ended of managed repos, via the collector feed
Power
Write only inside its home repo; read-only git state of managed repos

L2 · Fleet arch agent (next)

Identity
One context on the controlling computer
Sees
The collector's aggregate feed plus each machine's list_agents
Does
Matches a repo by remote URL across machines, picks one that is available, hands over the task
Needs
A cross-machine send with an actor field. The collector stays read-only

What you asked for, and what you decided on 2026-09-02

  1. A hierarchy of command with a new middle layer. Operator → Arch agent → Repo agents. You talk to one agent, it talks to many. The next task adds a fleet layer above it.
  2. Strict separation of concerns. The arch agent's medium toward repos is conversation plus read-only git state. No file or git power over any managed repo. It writes only in its own home repo.
  3. Provenance preserved end to end. An arch-assigned task appears in the repo agent's dock exactly as if you had typed it, tagged arch. You can open any dock and see what it is doing.
  4. The arch agent is its own UX. Not bound to one repository, so not a repo dock: a top-level Arch tab.

Availability and the run slot, simulated

Three managed repos. bironext starts on a branch you created, so it is claimed: the arch agent lists it but never sends to it or reads it. The composer under each dock is the real one: disabled while the slot is busy, whoever holds it.

Arch agent armed · idle

Feed and tool calls, as the arch loop sees them

What the simulation shows

  • Availability has four values. available slot free and branch is the default or one the arch assigned. busy slot running, any actor. claimed your branch; no sends, no reads. unmanaged not in the set; invisible.
  • Busy is an answer, not a queue. send_task on a busy repo returns busy and nothing is stashed. The arch agent is woken by that repo's turn.ended anyway, so it re-sends then.
  • Taking over. Stop the arch agent. The running repo turn is not cancelled; it runs to turn.ended. Then the slot is free and your message goes in. Or check out your own branch: the repo becomes claimed and the arch agent leaves it alone even while armed.
  • chat.focus shows up in the feed but is ignored. The watermark advances past it; no wake.

Wake-up is the event feed you already have

You built the feed so one controlling computer could hear agents start and finish on several machines and play sounds. The arch agent needs exactly that information, minus the sounds.

What exists (openspec: harness-event-feed, event-feed-collector)

  • Envelope: seq (monotonic, survives trims), at, type, source{repoId,repoName}, data. Ring of 1000, in-memory.
  • Types today: turn.start (fresh turnId), turn.ended (same turnId, status, cost, turns), chat.focus.
  • Read: GET /api/events?after=N, read-only, normal harness auth. New types need no reader change.
  • Collector: backend-owned, persisted source list, polls remote harnesses read-only, tags each event with its source, one fleet-wide seq.
  • Strictly read-only toward watched harnesses. Kept. Sending is a different channel.

How the arch loop uses it

  • The engine ticks every 10 s. The arch loop is one more ILoop, keyed @arch, and on each tick reads CollectorService.ReadEvents(after) with its own persisted watermark.
  • turn.start / turn.ended from managed repos become the wake prompt: "birocode finished (done, 3 turns). minesweeper running 06:12. bironext claimed on feature/x." Then one arch turn.
  • Nothing new, or only chat.focus, or only unmanaged repos: hold, watermark advances.
  • A fresh watermark starts at the collector's current last seq. No replay of history.
  • Each sent wake publishes arch.wake to the feed, so the board, the sounds and the future fleet arch can see the middle layer working.

Its own surface, and its own home

The home repository

  • What it is. A git repo folder that is the arch session's cwd and the only place it may write: CLAUDE.md (role prompt), memory/ (what it knows about each repo), assignments/<repo>.json (which branch it asked for, when, why).
  • Why assignments matter. They are what makes the availability rule work: a branch listed there is the arch's own work; any other branch is yours.
  • Where. assumption <ProjectsRoot>/arch-home, a sibling of birocode. You mentioned a subfolder inside birocode. A cwd inside the harness repo would let the CLI's file tools reach the harness source, and its git commands would act on birocode's history, which breaks "no power over any managed repo" structurally. A sibling keeps the fence real. Say the word and it is one config value.
  • Not a repo card. The Arch tab shows its path and recent commits; it does not appear in Projects or as a dock.

What stays where it is

  • Repo docks are unchanged except for the actor tag on non-human bubbles.
  • The Dashboard keeps showing running agents from the feed; an arch-driven turn looks like any other running agent, and arch.wake shows the middle layer.
  • Advanced mode only, by the UI-modes convention.

The next level: tell it a repository and a task

Your description of the fleet arch: you name a git repository and a task; it finds a computer that is not working on that repository and hands the task over. Everything in this change that makes that a scope change is marked.

Shaped for it in this change

  • list_agents returns machine, repoId, remoteUrl, branch, availability. Matching a repo across machines is a remote-URL equality.
  • send_task is addressed by (machine, repo); machine is self now and refused otherwise.
  • The arch loop reads the collector feed, already source-tagged per machine.
  • arch.wake lets a fleet arch see when a machine's arch agent acted.

Still missing for L2 (deliberately not in this change)

  • Actor on the wire. The remote chat POST has no actor field, so a fleet send would show as human in the remote dock.
  • A send channel that is not the collector. The collector spec says it never acts on a watched harness. Keep that; add an explicit outbound client.
  • Reaching an L1. @arch on a remote harness as the address, so the same send path reaches the middle manager.
