Management layer vs Execution layer openspec split-management-dashboard

Where the Arch agent and Ideas should live: a second dashboard now, a separate refresh-to-update app next — and why the arch brain never moves.
TermDefinition
HarnessThe deployed Claude Web app on each box — heavy backend: runs, loops, arch brain, collector. Redeploy = build + swap + dead-man switch.
Execution DashboardThe current dashboard: per-repo docks, runs, Autopilot, Agent Audit. "What are the agents doing right now on this box."
Management DashboardA new parallel top-level surface for direction-setting: the Arch agent and Ideas.
Management AppThe events app grown up: a separate static page that calls Harness REST APIs. Change it → refresh, no redeploy.
Arch BackendThe arch agent's server side: tools, loop, fleet client, audit. In-process C# inside the Harness — a static page cannot host it.

The observation. The dashboard's four summonable panels are two different kinds of thing. Autopilot and Agent Audit answer "what is running on this box, and what did it do" — execution. The Arch agent and Ideas answer "what should the fleet work on next" — management. Today all four sit in one rail, so the management tools look like just more execution widgets.

Why the split is real, not cosmetic. Underneath, everything management-flavoured is already fleet-scoped: the Arch agent scopes repos across machines, Ideas syncs across machines through the hub, the collector watches every harness. Everything execution-flavoured is box-scoped: docks, runs, the loop engine, the audit. The UI never caught up with the architecture.

The two-step plan. Phase 1 separates the surfaces inside the Harness (cheap, ships now). Phase 2 moves the management surface out of the Harness into the Management App (refresh-to-update, outlives any one harness). Phase 1 is deliberately thin — pure placement, components reused unchanged — so nothing built now is thrown away by phase 2.

Why the SPA talks to ONE harness, not N. A browser page calling many harnesses directly means CORS and a credential per box in the page. The pattern that already works is the collector's: the page speaks only to its home Harness — same origin through the proxy, so the session cookie just works — and that Harness relays to the fleet with the peer API and stored credentials it already has. Fleet reach comes free.

Why the Arch Backend never moves. send_task claims the builder run slot and spawns the CLI; the loop engine ticks the arch loop; the fleet client unprotects stored credentials. All of that is in-process server code. A static page has no process. So "move the arch agent to the events app" can only ever mean moving its face — which is cheap, because the Arch tab already does everything over REST.

What phase 2 actually is, then: port the Arch and Ideas UIs into the Management App's page, against the same endpoints they call today. The Harness's Management tab from phase 1 shrinks to an embed or a link. Nothing server-side changes.

Width and visibility persist per device; narrow screens stack as before.

Phase 3 — the arch agent keeps the fleet on one build openspec arch-peer-upgrades

The gap it closes. Every fleet feature so far assumed the peers run a compatible build, and every upgrade was a person at each box running swap.ps1. Now the hub's arch agent sees drift (list_machines carries version, hubVersion, behind) and can drive the peer's redeploy itself.

1 · notice
peer describe says build X, hub is build Y → behind
→
2 · posture
loop armed · sends allowed · peer accepts fleet upgrades · versions differ
→
3 · upgrade_peer
POST /api/arch/peer/upgrade {ref}
→
4 · the peer does it
ff-only pull on its branch · carry new config keys · detached swap.ps1 · dead-man switch
→
5 · keep is earned
new process finds the job file; running the target commit → disarm; else rollback

Why the peer owns the deploy. The receiving harness runs the same committed script its operator would, with the same guard and the same auto-rollback; the caller only says which ref. Refusals are honest and leave the tree untouched: not-on-branch, dirty, pull-failed, current, busy, not-accepting.

Two opt-ins, again. Sends must be allowed to that machine on the hub, and its operator must tick accept fleet upgrades on its own Arch tab. The Fleet card shows drift and offers an operator upgrade to this build button under the same rules — the arch agent and the human use one path.

Built 2026-09-05. Verified on an isolated instance (posture + API + Fleet card) and by a real self-upgrade of this box's live harness through the peer endpoint; the first MONSTER upgrade needs one last hand deploy there so it has the endpoint.

Constraints carried into the spec:

  • The Arch Backend stays in the Harness — restated from the 2026-09-02 decision; phase 2 must not be read as reopening it.
  • Phase 1 moves mounts only: the Arch page, Ideas panel and their APIs are reused unchanged, so phase 2 can lift them without unwinding anything.
  • The Execution Dashboard keeps Autopilot and Agent Audit exactly as they are; docks stay always-on.
  • New UI defaults to Advanced mode (repo convention); Basic mode never sees either dashboard.
