The engine has no idea which conversation it is driving

AutopilotService.LastAssistantMessage() defines "the agent's reply" as: the last assistant message of the newest .jsonl file in the repo's transcript folder. That folder is shared by every conversation touching the repo. Three things then break at once:

  1. Resume forks a new session. Every claude --resume <id> -p the loop fires writes a new session file (new session_id, full history copied — hence three ~165 MB files). The "newest file" is now the fork, not the conversation you watched.
  2. Other agents pollute the reply. The auto-understanding background job was writing turns in the same repo during the window. The engine read its messages as the loop agent's reply.
  3. Sentinel matches anywhere in the text. SentinelHit uses Contains("LOOP_DONE"). The auto-understanding agent wrote "…the 'reply OK until the 3rd ask, then LOOP_DONE' mechanism" — merely quoting the sentinel — and the goal loop flipped into its verify phase.
  4. The dedup guard is defeated. The "already sent against this reply" guard compares one snippet. Every time a different session file became newest, the snippet changed, the engine believed "the agent replied", and sent again — ~10s apart, far faster than any real turn.
  5. The cap counts sends, not turns. RecordSend bumps the counter on every dispatch, misfires included → 5/5 → status capped.

Backend-side it IS the same pipeline — the frontend just never looks

The loop send is not a shadow path: it claims the same run slot (RunSessionService.TryBeginRun), streams through the same CliRunnerService, and buffers the same seq-numbered events the Send button produces. The dock badge, /api/runs, everything backend-side is identical.

The gap is client-side attachment. The React chat only discovers a backend run at four moments — and "while you sit on an open page" is not one of them:

So when the autopilot starts a turn, the event buffer fills server-side, but no client is attached: no bubbles stream in, streaming stays false, and the composer keeps showing Send instead of the black Stop. A refresh remounts the app → reconcile() runs → it finally sees the run (or the finished transcript). Nothing was hidden on purpose; there is simply no push or poll signal for runs the client didn't start.

The shipped fix (openspec: fix-loop-conversation-identity)

A · The loop is pinned to ONE conversation

Implemented. The loop record carries a SessionId pin. Arming stamps it — the dock passes the conversation it is showing; API callers without one get the repo's newest session resolved once at arm time. The engine reads "the agent's reply" from the pinned session only (LastAssistantMessageIn) and resumes the pinned session only. Because every --resume forks a new session id, the pin advances on builder-lane RunCompleted to the run's captured id — loop-sent and human-sent turns both move it; background jobs (auto-understanding) never claim the builder lane, so they can't. Unrelated sessions can no longer feed, advance, or resolve a loop.

B · Completion tokens anchor to the final line

Implemented. LOOP_DONE and GOAL_VERIFIED count only on the reply's final non-empty line (case-insensitive, punctuation-tolerant) — exactly what the convention doc promises. A reply that merely quotes the sentinel does nothing. NEEDS_HUMAN: and the deny-list stay whole-reply substring matches: their false-positive direction is "stop and ask", the safe side.

C · The open page discovers engine-started runs

Implemented. ChatContext polls the in-memory /api/runs snapshot every ~5s while the page is visible and attaches through the existing reconcile() → attachToRun() path (idempotent — it no-ops while a reader is attached). An engine-started run now streams bubbles and flips Send to the black Stop on the open page, because it's the same streaming flag a manual Send flips.
