How to read it. The policeman is five parts (tab 0). The main machine is its lifecycle: harness code, a timer and a few caps (tab 1). One of its states, PASS RUNNING, hands control to the sub-machine: the model runs the prompt’s steps in order (tab 2). The model cannot touch anything directly; each acting step is a call through the fences to a tool, and the tool is code that reads or moves a card by the facts (tab 3). There is a second checker you may not have known about: the Board check, harness code that runs every minute and writes most of what a card shows; tab 4 sets the two side by side and draws the one loop they should become. Tab 5 is a clickable demo of the product tab that loop would get — fake data, nothing built — so you can judge the UI before any code moves. Scroll to zoom, drag to pan. Click a state to light its transitions; click it again, or the background, to clear. Click the dashed box to open the next level. What is deterministic (harness code) and what is prompt-driven (the model's judgement) is marked on every box and every arrow — the glyph on the box, the line style of the arrow, and the "colour: who decides" toggle. The rule of thumb: the harness owns timing, safety, facts, moves, fences and provenance; the model reads and judges inside a closed set of allowed writes. Positions are laid by hand so the picture is stable; the data (policemanStateMachine.js) is the module the client tests validate: every endpoint known, every state reachable, no dead end but the terminal ones, and nothing moves a card backwards. openspec kanban-policeman-conversation · policeman-tool-surface · policeman-syncs-cards · policeman-observes-agents.
