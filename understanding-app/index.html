What the Operator asked for

Every repo agent has an Understanding app — a self-contained SPA a subagent (re)builds to explain the latest turn. Goal conversations (the arch's goal loops, shown in the dashboard's Subagents tab) have a step plan and a live chat, but no Understanding app. They run complex orchestrations, so it matters most here.

The right pane of a selected goal stacks the step plan over the chat. Turn it into a tabbed view:

1 · Step plan
The stepper and its status, exactly as today — just moved into a tab.
2 · Chat
The goal/loop state and the conversation — composer, NEEDS_HUMAN answer box, stop/continue — everything that is there now.
3 · Understanding
An Understanding app for that goal conversation, on the same principles as the repo-agent feature. Ask the goal's chat to build it; see it rendered here.

Keep the left list as is. Remember the tab choice per goal. Pick sensible defaults (which tab opens first; a badge when a step is blocked). Do not break the step-plan or chat behaviour.

What exists today (verified in the code)

The repo-agent understanding/goal pipeline — one spine, keyed by AppBuildKind

Both the Understanding app and the Goal app are two instances of one pipeline. I reuse its shape, not its repo-coupling.

  • ClaudeWeb.App/Services/Understanding/AppBuildKind.cs — Understanding / Goal kinds; IConversationAppBuilder.BuildAsync(workingDir, sessionId, ct); ConversationAppBuild.RunAsync is the shared body (validate session → load transcript → one ephemeral, write-capable subagent in the repo root).
  • UnderstandingJobs.cs — backend-owned, latest-only job per (kind, repoId), its own cancellation token (a phone refresh never cancels a run), coalescing Auto slot.
  • UnderstandingAsk.cs / GoalAsk.cs — each owns only its prompt; points the subagent at docs/understanding-app-convention.md.
  • HarnessStaticApp.cs — no-store static serving of a build-less folder, contained (no traversal), explicit empty state / 404, no fallback.
  • LocalProxyController.cs — dispatches synthetic kind:harness app ids (understanding, goal, …) to their serve service; real apps proxy to 127.0.0.1:port.
  • client/.../useAppBuild.js + PinnedAgent.jsx — the 🧠 / 🎯 buttons + Auto, one shared client state machine keyed by a base string.

The goal conversations surface

  • client/src/components/arch/SubagentsPanel.jsx — left list of all goal conversations; right pane = GoalPlanPanel stacked over the Arch chat view. Polls /api/arch/conversations every 5 s.
  • GoalPlanPanel.jsx — the live stepper (done/active/blocked/skipped), mark-step, answer-a-blocked-step, continue-from-plan.
  • ClaudeWeb.App/Services/Arch/ — a goal lives as fields on its conversation record in <datadir>/arch.json; its transcript is a .jsonl under arch-home's CLI project dir. Endpoints are the /api/arch/goals/{id}/<verb> family.

Two constraints that shaped the design

constraint arch-home denies Write
The arch's .claude/settings.json structurally denies Write/Edit/Bash/Task/Agent. So the build subagent cannot author files in arch-home.
constraint Goal conversations are hub-local
FleetClient relays no goal/conversation verbs. A goal runs on the harness that started it; its app is naturally local — no fleet byte-relay to design.

Risks to existing goal conversations, and how I contain them

containedStep plan / chat behaviour
The three tabs are pure presentation: GoalPlanPanel and the Arch chat view are moved into tabs unchanged — same props, same endpoints, same handlers. Non-goal arch conversations keep the plain chat (no tabs).
containedNo arch role-prompt rewrite
No new MCP tool, no RoleVersionMarker bump — so no live arch home gets a rewritten CLAUDE.md. The build is a harness-owned subagent, outside the arch loop.
containedWrite blast radius
The subagent's cwd is <datadir>/goal-understanding/<goalId>/ and the prompt scopes it there. It cannot touch arch-home (denied) or any repo.
containedRun ownership
The job runs on a background task with its own cancellation token; a phone refresh mid-build never cancels it, and the tab reattaches via the status endpoint — the repo pipeline's proven model.
watchServing path
Served under /api/arch/goals/{id}/understanding/app/ (auth-gated, like the rest of /api/arch); the iframe loads with the dashboard session. Relative URLs only, no-store, no fallback — a broken app is visibly broken.
watchTranscript size
Long transcripts are exported to a side file and referenced, as the repo pipeline does past ~12 KB, so the prompt never balloons.
