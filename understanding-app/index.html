🗂 The hub file system — how a file gets from agent A to agent B

fleet task 3ad064a2 · openspec hub-file-system · three repo-agent tools + two arch tools on the existing MCP servers · a File System tab on the Management dashboard

The one trusted direction decides the shape

🔐
hub → peer is proven
the fleet client calls a peer's /api/arch/peer with the peer's stored password; writes there need the peer's "accept fleet sends" — the channel every task send already uses
→
🚫
peer → hub does not exist
a repo agent on MONSTER runs on MONSTER's harness, which holds no credential for the hub; inventing one would be a second trust model
→
🗂
so: one store per harness
%APPDATA%\ClaudeWeb\hubfs\ on every machine; a repo agent touches only its own machine's store
→
🏛
the arch is the bridge
hub_transfer(path, from, to): fetch a peer's file into the hub (kept there), push a hub file to a peer, or peer → peer through the hub — over the proven direction only

"Hub as a shared file system" therefore reads: every store is visible to the hub (the arch's hub_files, the File System tab), and the hub's arch moves files wherever they must go. On one machine nothing moves — B simply downloads what A uploaded.

"arch, have A upload its fixtures, then have B download them"

    The arch names the hub paths when it dispatches (prg/fixtures/customers.json), so A, B and the arch mean the same file; A's reply confirms the paths before anything is transferred. The role prompt (v14) carries this ritual.
