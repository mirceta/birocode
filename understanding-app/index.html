Loop evals — golden human runs as ground truth for autopilot loops

Is a change to a loop recipe better or worse at driving a long task? Instead of a static expected-answer file, the ground truth is a recorded human-babysat run: start state, plan, the finished conversation, and the repo state after every turn — packaged as a git history. The runner replays the production loop engine from the same start and the scorer compares outcomes and trajectories.

1The pipeline — click a stage

Five stages, two of them human-facing (babysit, curate) and three mechanical (validate, run, score).

2The bundle — a git history with three refs

A golden example is a directory: manifest.json + plan.md + conversation.jsonl + repo.bundle. The repo states live in the bundle as ordinary commits. Click a transcript turn to see which repo state it maps to — turns without their own commit carry the previous state forward.

Click a turn. Amber = the turn's own commit; carry = no commit was made after this turn, so its state is the previous one.

3Capture = retroactive curation (Loop Evals tab)

You only know a babysat session was golden when it's over. So capture is after-the-fact curation over two things that already exist: a copy of the repo (with its .git) and the session's stored conversation. Operator-facing, Advanced mode, api/loop-evals/*.

  1. Select sources — pick the repo (its stored conversations) and type the repo copy's path (its commit history, listed with files touched).
  2. Set the span — mark first/last relevant turn with [ ]; everything outside is excluded.
  3. Associate turns ↔ commits — select a turn (⇄), click a commit. One commit per turn; association is partial by nature.
  4. Label each turn — instruct, course-correct, approve, verify-ask, unblock, or free text. Labels ride in the transcript (reporting, not scoring).
  5. Author & export — write plan.md and the acceptance checks, then export the bundle into the examples root.
Contiguity rule: the associated commits must form an unbroken parent chain — the exported golden branch is exactly those commits in order. Skipping a commit in between is rejected: associate every commit in the stretch, or none of them.
Sources stay byte-identical: refs are cut in a throwaway clone, never in the repo copy; the stored conversation is only read. Export writes one place: the examples root (default %APPDATA%\ClaudeWeb\loop-evals-examples — external, because a bundle carries full repo history; committed examples under tests/loop-evals/examples/ must be synthetic).

4The runner — the real engine, isolated

LoopEvals run --example <id> hosts the production modules (AddChatModule / AddDockModule / AddPromptsModule / AddAutopilotModule) in-process against a scratch CLAUDEWEB_DATADIR — the same AutopilotService tick, recipes, and Claude CLI turns the harness runs, so changing shipped loop logic changes eval results.

6Reliability — N runs, not one

  
Loops are non-deterministic, so one pass proves little. --runs N repeats the same
  (example, config) into separate scratch clones and aggregates: pass rate, worst case, turn spread. A loop that
  passes 3/5 is a different animal from one that passes 5/5 — the report keeps them distinguishable.
  Every run costs real agent tokens; the runner is on-demand, developer-facing, never a service.
