Why the box crashes — what the harness does to the disk

Investigation of 4 hard crashes (2 – 3 Sep 2026) on the Claude Web host. Click a step in the chain to expand it. Use the tabs to move between the evidence, the mechanism, and the fixes.

1. The crashes are kernel bugchecks, not app crashes

Four "rebooted without cleanly shutting down" events in two days. Three left a bugcheck code; two left a minidump. The two minidumps were parsed by hand (no debugger on the box) and both stacks run through the same driver path.

What both minidump stacks contain
ntoskrnl ← FLTMGR.SYS ← WdFilter.sys (Windows Defender real-time filter) ← FLTMGR.SYS ← ntoskrnl (file I/O)

A user-mode app cannot bugcheck Windows by itself. The kernel died inside Defender's file-system filter while it was inspecting file operations. What the harness controls is how much file I/O it pushes through that filter.

Aggravating factors on this host (outside the harness)
  • OS Windows Server 2019 build 17763.1518 — last cumulative update installed 2023. The kernel is from 2020.
  • Defender platform 4.18.26070.9 (Aug 2026) running on that 2020 kernel. Real-time protection on, only one exclusion (the prg folder). None of the busy directories are excluded.
  • Drivers gdrv3.sys (Gigabyte, 2023, a driver with a public history of kernel bugs), IntelHaxm.sys 7.6.5 (2020, abandoned hypervisor driver) and gvm.sys (a second hypervisor driver) loaded side by side, npcap.sys, Intel Arc igdkmdn64.
  • Hardware 64 GB RAM, 24 cores, Samsung 980 PRO healthy, no WHEA hardware errors, no memory-exhaustion events. This is not a resources-ran-out crash.

2. The mechanism: 249 MB re-read every 5 seconds

Measured on the live harness while idle (no user clicks): 498 MB read in 10 s in 127 000 read operations of 4 KB each. Writes: nothing. That is one process — ClaudeWeb.exe — streaming the same file over and over.

Numbers from the live log (12:56 → 13:07, 10.5 min)
eventcountmeaning
"Loaded 6595 message(s) for session 194f3269"105one full parse of the 249 MB transcript every 6 s
"[GH-ACCT] authenticated as …"53two gh.exe processes + a GitHub API call every 10 s, for a header chip
"401 rejected GET /api/events"137a stale browser tab polling with a dead cookie (cheap, but noise)

One load: 1.24 s of server time, 249 MB read, 3.4 MB JSON sent to the browser. Per hour: ~150 GB read through Defender's filter, from a file another process (claude.exe) is appending to at the same time.

3. Where the disk and process churn comes from

Ranked by measured or estimated cost. The first two are the ones that scale with transcript size, which is what changed recently: this session's transcript grew to 249 MB.

Why it correlates with the crashes

Each crash happened minutes after a deploy or during a build-heavy agent turn, while a large session was running and a browser was open. Deploys add a vite build (thousands of small files), a dotnet build, a robocopy mirror of the run dir, and a Playwright Chromium profile, all on top of the 50 MB/s baseline. Every file open, read and close passes through WdFilter. The harness is the single biggest source of that traffic on the box.

4. Five highest-leverage optimizations

Ordered by (bytes or processes removed per hour) ÷ (effort). The first three remove more than 95 % of the measured baseline.

Outside the harness (do these too)
  • Add Defender exclusions for the busy trees: ~/.claude/projects, the playground root, .selfdev-build, .claudeweb-preview, %TEMP%\cw-loopeval, and the processes claude.exe, node.exe, dotnet.exe, ClaudeWeb.exe, git.exe.
  • Patch the OS. A 2020 kernel with a 2026 Defender filter is an untested pairing.
  • Remove IntelHaxm (deprecated) and check whether gvm.sys and gdrv3.sys are still needed.
