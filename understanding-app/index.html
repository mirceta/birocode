One loop model — unify-loop-types, revision 2

Every autopilot mode is now literally the same thing: a loop instance — { kind, mode, armed, agent } — whose kind is an implementation of one interface. The engine has no per-kind branching left; the dock has one section that says type · armed · mode.

ILoop.cs · SuggestionLoop / RecipeLoop / GoalLoop · LoopConfigStore.cs · AutopilotService.cs · DockLoopControl.jsx

ILoop — semantics in the kinds, mechanics in the engine

interface ILoop {
  string Kind;                       // "suggestion" | "recipe" | "goal"
  LoopDecision Decide(LoopContext);  // exactly one of:
}
LoopDecision.Hold    (reason, escalate?)          // stay armed, do nothing this turn
LoopDecision.Stop    (status, reason, detail)     // terminal: done / escalate / error
LoopDecision.Propose (prompt, enterPhase?)        // "the agent's NEXT prompt is this"

The engine (AutopilotService.Tick) does the same thing for every agent: find its one active instance, ask the kind's implementation for a decision, execute it. Idle detection, dedup, the cap check, sending, pending-prompt recording, and auditing are shared mechanics — identical for all three kinds.

💡 SuggestionLoop

Wraps the PromptClassifier: which of your routine prompts comes next?

  • Confident, non-risky verdict → Propose(label)
  • Unclear / risky → Hold — non-terminal, stays armed
  • Uncapped by default; no sentinel, no "done"

📋 RecipeLoop

Drives one stored ritual prompt (e.g. "Drive the OpenSpec change").

  • Sentinel LOOP_DONE → Stop(done)
  • Otherwise → Propose(stored prompt)

🎯 GoalLoop

Free-text goal; work + verification prompts composed once at arm time.

  • Work + done-claim → Propose(verify prompt, phase→verify)
  • Verify + GOAL_VERIFIED → Stop(done, verified)
  • Verify + gaps → Propose(work prompt, phase→work)

Shared safety ladder — DrivenLoop base (recipe + goal)

run errored → Stop(error)→ NEEDS_HUMAN → Stop(escalate)→ deny-list word → Stop(escalate)→ kind's own DecideCore

NEEDS_HUMAN outranks the sentinel — a reply carrying both means blocked, not done. All matching is deterministic string search; no LLM judge. The suggestion kind doesn't use this ladder: it never drives a blocked agent (its escalations are non-terminal holds), and its risk handling is the classifier gate.

Exclusive arming is now structural — the coordinator is gone

LoopConfigStore holds one dictionary slot per agent. Arming any kind replaces the slot, so "at most one autopilot mode per agent" can't be violated — it isn't a rule anyone enforces, it's the shape of the data. AutopilotArming was deleted; legacy suggestion arming (autopilot.json ArmedRepoIds + the global auto-advance flag) drains into suggestion instances once at startup. One Disarm clears whatever runs. A fresh arm also resets the engine's dedup guards, so a new loop acts on the agent's current message immediately.

💡 armed— arm 🎯 → slot now holds 🎯 (💡 displaced)— Disarm → slot stopped

The common axis: what happens to a proposed next prompt

A loop's whole job is to decide the agent's next prompt. The instance's mode decides what that means — for every kind:

modea Propose(prompt) becomes…
suggestthe instance's pending prompt — shown on the dock with "Put in chat box", pre-filling the composer. Nothing is sent; the counter doesn't advance; the loop waits until the agent's reply changes (i.e. until you send something).
driveactually sent to the agent (resuming its session through the same run path the chat uses) — capped, audited, double-send-guarded.
This dissolves the old special case: "auto-advance" was a private, global flag of the suggestion mode. Now it's a per-instance property of every loop — a recipe or goal loop can run human-paced (each turn lands in your textbox for approval), and the suggestion watcher can drive. The mode flips live without resetting the loop. The old global toggle survives as the default mode for newly armed suggestion instances (and flips armed ones, keeping its old meaning).

Cap & disclosure follow the mode

The iteration cap bounds drive-mode sends only (suggest mode never sends; suggestion instances default to uncapped). A pending prompt is prompt TEXT, so the ungated status projection carries it only while the operator gate is open — gate closed means the engine is idle and pends nothing, so the closed-gate disclosure surface is unchanged: kind, mode, phase, counts, stop reason stay visible; text never leaks.

Why verification before "done"

A recipe's steps are externally checkable, so its LOOP_DONE is trusted. A goal is a claim about the world — so the goal kind turns the done-claim into a verification turn (re-check the ACTUAL repo state: build, tests, app) and only the distinct GOAL_VERIFIED token in that turn's reply ends the loop. A failed verification feeds what's missing straight into the next work turn.

Surprise 1 — a phantom claude.exe was co-driving the repo

Mid-turn, files I hadn't touched kept changing. Cause: a second, orphaned claude.exe — spawned by a since-dead harness instance — was still running the user's previous turn with --resume <this same session id>. Two runs interleaved into one transcript and edited the same worktree; it even wrote its own variants of files I was writing. Detached runs deliberately outlive disconnects, so when the parent harness dies the run is orphaned with no API to stop it.

Surprise 2 — the tests caught a real engine bug: re-arm was ignored

      acting twice on the same agent message) used to survive re-arming. So a freshly armed loop would look at
      the agent's current reply, decide "already handled that message," and sit idle for a whole turn. Fix: every
      instance carries an ArmedAt generation stamp; on a new arm the engine resets its guards, so
