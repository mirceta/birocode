  • Two sections under every machine — Occupied on top, Free below, each with its count; an empty one says "none".
  • At a glance — occupied chips have an amber left edge and a faint hatch, free chips a green edge; ✋ marks a setting the Operator made.
  • Click an agent — its details gain the three-way control and a line saying what is in effect and who decided. The change is immediate and survives refresh and restart.
  • Filter chips became free / occupied (occupancy-based); a saved "on main" / "not on main" choice maps onto them.
  • The motivating case: web-flow-autodev is on a feature branch, so the Operator marks prg occupied although it sits on main — and the arch now treats prg as claimed.

Where the setting lives, and what a peer sees

  • %APPDATA%\ClaudeWeb\occupancy.json on the harness that set it: { "<sourceId>|<repoId>": { occupied, setAt, setBy, note } }, empty sourceId = this machine (the board's assignee key). POST /api/arch/fleet/occupancy { sourceId?, repoId, occupied: true | false | null }.
  • A setting made on the hub about a peer's agent colours the hub's view: its Status tab, its arch's list_agents, its sends over the fleet (refused locally as claimed). The peer's own harness does not learn it.
  • A setting made on a peer about its own agent travels with that peer's describe (availability / claimedReason) to every hub — but the hub's tab shows it as the branch rule, because the describe carries no occupancy object yet. Follow-up: add occupancy to the describe.
  • Groups (proposed, not built): an optional group label per agent in the same store; setting any member sets the group; the tab brackets members. One more field and one store method.
