Why the 💡 suggestion loop did nothing — and what changed

openspec change fix-suggestion-loop-inert · diagnosed live 2026-07-28 · rolling latest Understanding app

The observed symptom

You armed 💡 on this repo in drive mode (19:57:25), watched ~30 s of nothing — no send, no pending prompt, no visible state — and disarmed (19:57:54). A second suggestion loop (web-flow-autodev) had been "looping" for a day on a repo folder that no longer exists.

Four stacked causes

#CauseMechanism
1Classifier could ~never fire Every routine's base confidence was exactly 0.85 (mining enrichment needs the prompt text to equal a mined key — never true for long prompts). Threshold 0.75 ⇒ the agent's reply had to contain ≥ 88% match strength of your prompt's own wording. So every tick ended in a silent escalate-hold.
2Holds invisible at the dock The decision + reason lived only in the Advanced Autopilot console. The dock — where you armed — showed just the armed badge. "Armed but holding" looked identical to "broken".
3Deny-list matched substrings "…merge to master…" inside a prompt permanently blocked that routine ("prod" blocked "production"), with no visible reason.
4Missing repos skipped silently Tick() iterated only repos whose folder exists — an armed loop on a deleted repo got no state, no log, no resolution. Forever "looping".

The four fixes (slice 1) + the real brain (slice 2)

FixNowWhere
Suggest mode always pends The classifier's best candidate becomes the pending prompt even below the threshold, with its honest confidence shown ("· 42% sure"). A human still sends every suggest-mode prompt, so the threshold keeps gating only drive-mode sends — safety unchanged. SuggestionLoop.cs (D1)
Decisions visible at the dock The loop popover shows the engine's live decision word (always) and its reason/confidence (gate open — same disclosure rule as the pending prompt). AutopilotController.cs · DockLoopControl.jsx (D3)
Deny-list word-scoped + named "prod" no longer blocks "production"; a real hit escalates with the term named: routine contains deny-listed "prod". A deny-listed routine is never pended or sent in any mode. PromptClassifier.ContainsWholeWord (D4)
Missing repo ⇒ explicit error An armed loop on a deleted/moved repo resolves once as error / repo-missing — the dock shows a terminal state. The live web-flow-autodev zombie self-resolves on the first tick after deploy. AutopilotService.Tick (D2)
A real classifier Default brain is now a one-shot claude -p call (fast model) that picks one of your prompts or abstains — this is what makes drive-mode sends actually reachable. Stub stays as fallback + config choice. See tab 4. CliPromptClassifier.cs (D5)

What deliberately did not change

Drive-mode safety: threshold + word-scoped deny-list + kill switch + operator gate still fence every automatic send. The brain can only ever pick from your editable prompt library — never free text. Recipe/goal kinds, the conversation pin, and arm-freshness rules are untouched. Note: the default deny-list (deploy · push · merge · …) still blocks routines containing those words — now as whole words, with the term named in the visible reason so you can curate the list.

The CLI brain, in one pass

tick sees NEW trailing agent message
  └─ Brain == "cli"?  ──no──▶ stub classifies synchronously
       │yes
       ├─ cache hit for this message?  ──yes──▶ consume verdict, decide
       ├─ classification in flight?    ──yes──▶ HOLD "classifying with the CLI brain…" (tick never blocks)
       └─ else: start ONE background call
            claude -p (stdin prompt) --output-format json --model haiku
            ├─ reply: {"index": N | -1, "confidence": 0..1, "reason": "…"}
            ├─ index → one of YOUR routine prompts (never free text) → deny fence → threshold
            └─ error/timeout/unparseable ⇒ stub verdict, reason notes "cli fallback (…)"

One CLI call per new agent message per armed repo (single-flight per repo, cache keyed by message). Selectable in the console's Control bar ("Claude brain" toggle) and persisted as autopilot.json · Brain ("cli" default | "stub"); model in BrainModel (default "haiku").
