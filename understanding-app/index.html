Two takes on evaluating the loop loop-eval loop-evals

The autopilot-loops engine drives an agent through long tasks a human used to babysit. How do we know a loop is any good? Two answers landed at once — almost the same name, different philosophies.

Built as the Understanding app for the feat/loop-evals branch after merging main. Both capabilities now live side by side in the tree.

loop-eval main shipped

An end-to-end acceptance gate. A committed suite that boots the real harness and drives a loop through the real shipped HTTP surface, then checks: did the canned job get done?

  • Ground truth: hand-authored synthetic fixtures — a mini repo template plus a goal-check.mjs script, or an expected.json of prompt→path→regex triples.
  • Runs via: external Node scripts → login, register repo, seed chat, arm loop, poll. Isolated throwaway instance, or --live against your running harness.
  • Scores: a binary hard-assertion ladder (loop status + ground-truth check + bookkeeping). One run.
  • You watch it: Tests-tab SSE runner, dock binding, --describe manifests.

Answers: "Can the loop still finish a canned job, end to end?"

loop-evals ours on branch

A golden-trajectory measurement instrument. Capture one real human-babysat task, then replay a loop from the same start and measure how close it drove to the human's path.

  • Ground truth: captured from a real session — start state + plan + full transcript + the repo state after every turn, packaged as a git bundle.
  • Authored via: a retroactive curation UI — pick a past session, set the turn span, join turns to commits, label each turn, write the plan + acceptance checks, export.
  • Runs via: an in-process runner hosting the real loop services from the start state.
  • Scores: acceptance verdict + trajectory (per-turn overlap with the human) + N-run reliability.

Answers: "How close to a human did the loop actually drive — and how reliably?"

Not duplicates — different rungs of the same ladder

They share the goal (measure the loop) but differ on ground truth (synthetic vs captured-from-real), scoring (binary vs trajectory + reliability), and run path (real HTTP surface vs in-process). loop-eval is the cheap, fast before-ship regression gate; loop-evals is the deeper tuning / benchmarking instrument. Keeping both is the point of the merge.

loop-eval — a run main

1 · Author fixture (by hand)
A tiny synthetic repo template + a ground-truth check (goal-check.mjs / expected.json). Committed.
↓
2 · Boot a target
Isolated throwaway instance (gate + kill-switch seeded to files before boot), or --live your harness.
↓
3 · Drive the shipped surface
Node script: login → register repo → seed chat → arm loop → poll. No engine bypass.
↓
4 · Assert & verdict
Binary ladder: loop status done·verified/drained + ground-truth check passes + iterations ≤ cap. Exit code + JSON.

loop-evals — a run ours

1 · Capture golden example
Curation UI over a real session: span → turn↔commit → labels → plan + checks → repo.bundle.
↓
2 · Restore start state
Clone repo.bundle at eval/start into scratch space.
↓
3 · Replay the loop in-process
Host the real loop services on the scratch repo, seed from plan.md, commit each turn to run/n.
↓
4 · Score: verdict + trajectory + N
Acceptance checks pass? + per-turn overlap vs the golden branch + pass-rate/spread across N runs.

The Hybrid — converge, don't compete

Reuse each side's strength as a separate layer:

  • Execution + observability layer ← from loop-eval: the proven E2E driver, the isolated-instance harness, and the watchable Tests-tab / dock skin.
  • Ground-truth + scoring layer ← from loop-evals: captured golden examples and the trajectory + reliability scorer.

Result: main's low-risk run path and operator UX, raised to a real-human fidelity ceiling.

Recommendation

Keep both; aim at the Hybrid. Ship loop-eval as the cheap before-ship regression gate now; keep growing loop-evals as the tuning instrument. The one piece of debt to settle first is the singular/plural naming collision — decide a single umbrella name before either grows further.
